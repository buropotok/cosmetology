# Yandex Cloud CD from GitHub

This document records the non-obvious details discovered while configuring continuous deployment from GitHub Actions to the Yandex Cloud VK contour.

## Repository layout

The Yandex contour is kept at the same architectural level as the Cloudflare contour:

```text
yandex/
└── vk/
    ├── function/          # Yandex Cloud Function source
    ├── miniapp/           # VK Mini App static assets
    └── gateway/
        └── openapi.yaml.tpl
```

Deployment workflow:

```text
.github/workflows/yandex-vk.yml
```

A push to `main` affecting `yandex/vk/**` or the workflow itself triggers deployment. `workflow_dispatch` is also available for manual runs.

The deployment updates the complete Yandex VK contour: Cloud Function, Mini App assets in Object Storage, and API Gateway.

## Workload Identity Federation

GitHub authenticates to Yandex Cloud through Workload Identity Federation (OIDC). No long-lived Yandex IAM key is required for the GitHub deploy identity.

The deploy service account is:

```text
github-deploy
```

The federation is:

```text
github-actions
```

The federation settings used by this repository are:

```text
Issuer:   https://token.actions.githubusercontent.com
Audience: https://github.com/buropotok
```

The workflow must grant GitHub permission to issue an OIDC token:

```yaml
permissions:
  contents: read
  id-token: write
```

`YC_DEPLOY_SA_ID` must contain the **service account ID of `github-deploy`**, not the federation ID, function ID, or service account name.

`YC_FOLDER_ID` must contain the Yandex Cloud folder ID containing the deployed resources.

## Critical GitHub OIDC subject detail

The main issue discovered during setup was the actual `sub` claim generated by GitHub.

The initially expected subject was:

```text
repo:buropotok/cosmetology:ref:refs/heads/main
```

However, the real OIDC JWT issued for this repository contained:

```text
repo:buropotok@262182803/cosmetology@1337130143:ref:refs/heads/main
```

Yandex Cloud performs an exact match between the external OIDC subject and the federated credential attached to the service account. Therefore the federated credential for `github-deploy` must use the **actual subject emitted by GitHub**, including the numeric owner and repository IDs.

This mismatch produced the following token-exchange failure:

```text
HTTP 401
invalid_client
No matching federated credentials for specified service account,
issuer and external subject
```

The failure happened before any Cloud Functions API call. Changing Cloud Functions roles could not fix it.

### Diagnostic rule

If GitHub → Yandex authentication starts returning `401`, inspect the real JWT claims rather than assuming the documented subject format. At minimum compare:

```text
iss
aud
sub
```

For the working configuration discovered during setup:

```text
iss = https://token.actions.githubusercontent.com
aud = https://github.com/buropotok
sub = repo:buropotok@262182803/cosmetology@1337130143:ref:refs/heads/main
```

Do not log the raw JWT, GitHub OIDC request token, Yandex access token, refresh token, or static Object Storage secret.

## Service accounts and permissions

There are two separate responsibilities.

### `github-deploy`

Used only by GitHub CI/CD through Workload Identity Federation. It needs deployment permissions for the Yandex resources managed by the workflow.

During initial setup `serverless.functions.admin` was granted for Cloud Function deployment. Additional permissions required by the complete contour should remain deployment-specific rather than reusing runtime credentials.

### `cf-service-account`

Runtime service account used by the deployed Cloud Function and API Gateway integrations. It is separate from `github-deploy`.

Do not use the runtime service account as the GitHub deployment identity.

## GitHub repository configuration

Repository variables:

```text
YC_FOLDER_ID
YC_DEPLOY_SA_ID
```

Runtime Object Storage credentials currently used by the function are stored as GitHub Actions secrets:

```text
YC_S3_ACCESS_KEY_ID
YC_S3_SECRET_ACCESS_KEY
```

These values must never be committed to the repository or printed in Actions logs.

For production hardening, runtime secrets should be moved to an appropriate Yandex secret-management mechanism rather than remaining plain function environment values indefinitely.

## Cloud Function deployment

The workflow deploys:

```text
yandex/vk/function/
```

into the Yandex Cloud Function:

```text
cosmetology-social-publisher
```

Runtime configuration currently uses Node.js 22 and entry point:

```text
index.handler
```

Yandex keeps previous function versions in `Active` state. `Active` means the version is valid and callable; it does **not** mean every Active version is the version currently selected by API Gateway.

The newly deployed version receives the relevant tags, including `$latest`. API Gateway uses the configured tag to resolve the version. Therefore seeing several historical versions with status `Active` is normal.

## Object Storage layout

Runtime images use the bucket:

```text
cosmetology-publisher-images
```

Artifact image keys must preserve the `artifacts/` prefix. The tested layout is:

```text
cosmetology-publisher-images
└── artifacts
    └── <artifact-id>
        └── <image-file>
```

For the original infrastructure test the exact key was:

```text
artifacts/test-artifact-001/cosmo-sofa.svg
```

Omitting `artifacts/` causes `NoSuchKey` even when S3 authentication and bucket permissions are correct.

The VK Mini App static files are deployed separately under the Mini App prefix managed by the workflow; runtime artifact images and application static assets should remain conceptually separate even if Object Storage is used for both delivery roles.

## API Gateway deployment

The API Gateway specification is stored in GitHub as:

```text
yandex/vk/gateway/openapi.yaml.tpl
```

The workflow renders the deployment-specific identifiers and updates the existing API Gateway from that specification. This makes the gateway configuration reproducible from the repository instead of leaving it as console-only state.

The gateway routes Cloud Function API endpoints and Mini App static assets. The function integration resolves the current deployed function version through the configured tag.

## Failure classification

When troubleshooting CD, identify the layer before changing permissions or code:

1. **GitHub OIDC acquisition failure** — check `id-token: write` and GitHub Actions OIDC environment.
2. **Yandex token exchange returns 401** — compare federation issuer, audience, service account ID, and especially the exact real `sub` claim.
3. **Token exchange succeeds but deployment is forbidden** — inspect IAM roles for `github-deploy`.
4. **Function deploy succeeds but runtime fails** — inspect `cf-service-account`, runtime environment and application logs.
5. **Object Storage returns `NoSuchKey`** — verify the complete object key including `artifacts/` before changing credentials.
6. **Gateway deploy/update fails** — validate rendered OpenAPI and deploy service-account permissions separately from function runtime permissions.

This distinction was important during initial setup: the repeated `401` was an OIDC federated-credential mismatch and occurred before Cloud Functions authorization, so adding Cloud Functions permissions was not a meaningful fix.

## Verified CD result

The first successful GitHub-driven deployment established the complete chain:

```text
GitHub push
  → GitHub OIDC
  → Yandex Workload Identity Federation
  → github-deploy
  → Cloud Function deployment
  → Object Storage Mini App deployment
  → API Gateway update
```

The Yandex Cloud console confirmed a new Node.js 22 function version with the `main` and `$latest` tags after the GitHub Actions deployment.
