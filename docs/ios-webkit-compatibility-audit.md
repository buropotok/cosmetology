# Аудит Mini App на совместимость с iOS / WKWebView

Дата статического аудита: 2026-09-08.

## Область и ограничения проверки

Проверены клиентские файлы `miniapp/`: критический путь загрузки, навигация,
Telegram WebApp API, работа с изображениями, редакторы, отмена запросов и CSS.
Проверка была статической и дополнена существующими Node-тестами. Она не заменяет
прогон внутри Telegram на реальных iPhone: в репозитории нет зафиксированной
минимальной версии iOS, BrowserStack/WebKit-матрицы или E2E-сценария для Telegram
WKWebView.

Под «блокировкой» ниже понимается один из сценариев:

- приложение остаётся без Home/навигации;
- пользователь не может завершить основной сценарий;
- экран или операция остаются в pending-состоянии без восстановления;
- web content process может быть выгружен из-за пикового потребления памяти.

## Резюме

Найдены **два критических архитектурных риска**, способных оставить Mini App без
Home, **четыре высоких риска**, способных заблокировать отдельный основной
сценарий, и несколько визуальных/эксплуатационных рисков.

Главный вывод: самая вероятная причина полностью неработающего приложения на iOS
до исправления была связана не с отдельной WebKit API, а с последовательным
bootstrap. В рамках исправления shell отделён от feature runtimes; оставшиеся
пункты ниже сохраняются как реестр рисков и критериев регрессии.

## Зафиксированная архитектура загрузки

- `bootstrap.js` загружает только Telegram gateway, router и Home navigation.
- Settings загружается через `settings-runtime.js` при открытии экрана.
- New Post/Composer загружается через `new-post-runtime.js` при выборе New Post
  или Continue.
- Before/After controller загружается только при входе в Before/After.
- Onboarding имеет собственный `onboarding-runtime.js`, общий для Settings и
  publishing integration, но не является условием запуска Home.
- Rich editor больше не загружается из AI mock-модуля: его lifecycle принадлежит
  `composer-rich-editor-runtime.js`.
- Ошибка publishing integration оставляет редактор доступным, но блокирует кнопки
  публикации и показывает локальное сообщение.

## Критические риски (P0)

### P0.1. Опциональные feature-модули блокируют Home

**Статус: исправлено архитектурным разделением runtime; защищается тестами.**

**Исходное наблюдение.** `bootstrap.js` последовательно ожидал `loadPlatform()`,
`loadOnboardingAndSettings()`, `loadAppShell()`, `loadComposerRuntime()` и
`loadRuntimeIntegrations()`. При этом `loadAppShell()` до `navigation.js`
загружает Before/After и AI-модули, а Home создаётся и показывается только при
выполнении `navigation.js`.

**Почему опасно на iOS.** Любая ошибка скачивания модуля, ошибка разбора
JavaScript, исключение при import-time DOM-инициализации или WebKit-особенность в
одном из feature-модулей останавливает цепочку. В исходном HTML все экраны скрыты,
а статического Home нет. Результат — пустой Mini App вместо локальной деградации
одной функции.

**Дополнительный фактор.** `index.html` синхронно загружает удалённый
`https://telegram.org/js/telegram-web-app.js` в `<head>`. Медленная загрузка этого
ресурса задерживает разбор body и запуск module-script. Это не единственная точка
отказа (код местами допускает отсутствие `window.Telegram`), но делает время
появления shell зависимым от внешнего origin.

**Рекомендация.** Создавать и показывать статический/минимальный Home после
загрузки только Telegram gateway и router. Composer, AI, Before/After, settings и
draft runtime загружать по lifecycle соответствующего экрана. Ошибки dynamic
import обрабатывать на границе конкретной функции и оставлять Home рабочим. Не
исправлять это общим `catch` вокруг всего bootstrap: он лишь покажет частично
инициализированный DOM.

**Критерий закрытия.** Автотест должен подтверждать, что Home отображается, если
каждый feature import по отдельности отклоняется.

### P0.2. Не определён и не проверяется JavaScript target для WKWebView

**Статус: частично снижено — `??=` удалён из bootstrap, но support target и
транспиляция всё ещё не зафиксированы.**

**Наблюдение.** Mini App отдается как набор исходных ES modules без build-step или
legacy bundle. В критических модулях используются optional chaining, dynamic
`import()` и async functions.

**Почему опасно.** На WKWebView, который не понимает хотя бы один синтаксический
конструкт, файл не начинает выполняться вообще. Feature detection не помогает при
parse-time ошибке. При несовместимом JavaScriptCore не будет ни promise готовности,
ни Home, ни сообщения об ошибке.

**Рекомендация.** Явно зафиксировать минимальную iOS-версию, поддерживаемую
продуктом, и добавить проверяемый browserslist/target. Либо транспилировать весь
критический shell до этого target, либо заменить новый синтаксис в shell и
запретить его статическим compatibility-тестом. Feature-модули всё равно должны
быть отделены от shell согласно P0.1.

**Критерий закрытия.** CI собирает/проверяет клиент для заявленного iOS target, а
smoke test открывает Home на самой старой поддерживаемой версии.

## Высокие риски (P1)

### P1.1. Нестандартное значение `behavior: 'instant'` находится в навигации

**Статус: исправлено; router использует совместимый `scrollTo(0, 0)`.**

`app-router.js` вызывает `window.scrollTo({behavior:'instant'})` при каждом
переходе, включая первый показ Home. Такое же значение применяется при закрытии
Before/After. Стандартно переносимыми значениями являются `auto` и `smooth`;
реакция на неизвестное enum-значение различается между реализациями и версиями.
Если WKWebView выбросит исключение, `router.show('home')` завершится до окончания
инициализации навигации.

**Рекомендация.** Использовать `behavior: 'auto'` или двухаргументный
`scrollTo(0, 0)` в compatibility adapter. Добавить тест, где `scrollTo` отклоняет
неизвестное значение, и убедиться, что Home всё равно показывается.

### P1.2. Pointer capture в основном фоторедакторе

В `before-after/editor.js` обработчик `pointerdown` без проверки вызывает
`stage.setPointerCapture(e.pointerId)`. Для resize-контрола уже существует
осознанная iOS-совместимая реализация с window-level pointer listeners и прямым
комментарием не использовать pointer capture, но редактор фотографии сохраняет
другую стратегию.

**Воздействие.** Ошибка/потеря capture в WKWebView может оборвать pan/pinch,
оставить `pointers` и `gesture` в несогласованном состоянии или полностью
заблокировать редактирование изображения. `pointerdown` не защищён локальной
совместимой веткой.

**Рекомендация.** Унифицировать gesture lifecycle с уже используемой в
`before-after/resize.js` стратегией: window-level listeners, `pointercancel`,
детерминированная очистка при close/unmount. Проверить одиночное перемещение,
pinch, уход пальца за пределы stage и системное прерывание жеста на iOS.

### P1.3. `DataTransfer()` является обязательной частью изменения набора фото

`composer-image-manager.js` проверяет только `typeof DataTransfer`, после чего без
защиты вызывает `new DataTransfer()` и присваивает `input.files`. Такой же паттерн
встречается в AI/manual transfer. Наличие имени конструктора не гарантирует, что
конструктор доступен и что WKWebView разрешит программное присваивание `FileList`.

**Воздействие.** Удаление, восстановление, замена и добавление сгенерированного
фото могут не обновить `<input>`. В `notifyChange()` исключение прерывает весь
сценарий; fallback-модели файлов нет.

**Рекомендация.** Сделать `composer-image-manager` владельцем массива `File` и
передавать его публикации/черновику через явный API, не используя DOM `FileList`
как transport. Присваивание через `DataTransfer` оставить только как best-effort
адаптер с capability probe (`construct + add + assign`) и локальным fallback.

### P1.4. Нет ограничений на декодирование исходных изображений

Before/After хранит исходные `Image` и рисует их на canvas через
`naturalWidth`/`naturalHeight`. Итоговый canvas ограничен примерно 1080 px по
ширине, но исходное фото до отрисовки декодируется целиком. Одновременно могут
существовать исходные изображения, object URLs, preview-копии, iframe редактора и
canvas. Кроме того, URL временного base canvas в `openWatermark()` освобождается
только внутри следующего `requestAnimationFrame`; если загрузка watermark или
переход прерывается раньше, cleanup не гарантирован.

**Почему опасно на iOS.** Пики памяти при декодировании нескольких современных
фотографий способны привести не только к ошибке операции, но и к завершению web
content process; JavaScript `catch` это не восстановит.

**Рекомендация.** Ввести принадлежащий image pipeline лимит размеров/пикселей,
ранний downscale до рабочей геометрии, последовательное декодирование и единый
реестр object URL с cleanup на success, error, cancel и unmount. Проверить HEIC и
фото 12/24/48 МП на реальных устройствах.

## Средние риски (P2)

### P2.1. Cancellation полагается на неодинаковое поведение AbortController

`draft-store.js` передаёт строковую причину в `controller.abort(reason)`, а AI flow
определяет отмену только по `error.name === 'AbortError'`. Использования
`AbortSignal.reason` нет, поэтому строка сейчас не нужна. На разных поколениях
WebKit форма исключения при отмене fetch и момент завершения promise различались.

**Рекомендация.** Вызывать совместимый `abort()` без reason, классифицировать
отмену также по принадлежности активному controller и `signal.aborted`, а не
только по имени ошибки. Добавить тесты navigation-away, repeated request и stale
completion.

### P2.2. Viewport и клавиатура учитываются только статическим `100vh`

Shell и Composer используют `min-height:100vh`; подписки на Telegram
`viewportChanged`/`safeAreaChanged` и `contentSafeAreaChanged` отсутствуют. При
появлении iOS-клавиатуры или изменении высоты Telegram viewport нижние действия
могут оказаться за клавиатурой. `env(safe-area-inset-*)` используется, но не
решает динамическую высоту viewport.

**Рекомендация.** В узком platform adapter поддерживать CSS custom properties из
Telegram viewport/safe-area API с fallback на `visualViewport` и обычные `vh`.
Не распределять проверки iOS по feature-модулям. Проверить focus редактора,
закрытие клавиатуры и возврат высоты экрана.

### P2.3. Современный CSS не имеет явных fallback до объявления

В основных стилях используются `color-mix()` и `aspect-ratio`. Если конкретный
WKWebView не поддержит декларацию, она будет отброшена. Для части полей граница и
focus ring тогда исчезнут, а у preview может потеряться квадратная геометрия.
Это обычно не блокирует JavaScript, но ухудшает доступность и может сделать
контролы визуально непонятными.

**Рекомендация.** Перед современными декларациями задавать обычное значение, а
улучшение помещать следом или в `@supports`. Для функционально важной геометрии
иметь width/height fallback.

### P2.4. Import-time listeners и observers не имеют lifecycle cleanup

Несколько модулей создают `MutationObserver`, глобальные `focus`, `pageshow`,
`visibilitychange`, pointer и custom-event listeners при импорте. Большинство
инициализаторов не возвращает `destroy()` и рассчитывает на единственный полный
page lifecycle. Это усиливает риск повторных действий после bfcache/pageshow или
частичного повторного монтажа.

**Рекомендация.** Перенести подписки в явные mount/unmount владельцев. Observer
оставлять только на root компонента и отключать при уничтожении. Не исправлять
проблему глобальным observer или повторной инициализацией bootstrap.

## Что уже сделано правильно

- Safe-area включён через `viewport-fit=cover`, а основные экраны используют
  `env(safe-area-inset-top/bottom)`.
- В resize-контроле Before/After уже отказались от pointer capture в пользу
  window-level событий и предусмотрели `pointercancel` и `destroy()`.
- Draft restore проверяет generation/version перед применением асинхронного
  результата, что защищает от части stale completions.
- AI request владеет controller и не применяет результат старого запроса к новому
  controller.
- Object URLs preview-фотографий в основном потоке освобождаются при замене и
  очистке.
- Доступ к большей части необязательного Telegram API защищён optional chaining и
  имеет локальные fallback или сообщения об ошибке.

## Рекомендуемый порядок исправлений

1. **Зафиксировать support matrix:** минимальные iOS, Telegram и WebApp API version.
2. **Разделить bootstrap:** сначала shell/Home, затем lifecycle-based imports.
3. **Ввести smoke-тест отказа:** по одному сломанному feature import, Home доступен.
4. **Определить JS/CSS target:** transpilation или статически проверяемый subset.
5. **Убрать `behavior:'instant'` из инфраструктуры навигации.**
6. **Унифицировать pointer lifecycle Before/After для WKWebView.**
7. **Отвязать модель файлов Composer от программного `input.files`.**
8. **Ограничить image decode/memory и централизовать cleanup object URLs.**
9. **Добавить viewport adapter и CSS fallback.**
10. **Прогнать матрицу реальных устройств** до выпуска.

## Минимальная ручная матрица перед релизом

На самой старой поддерживаемой iOS и на актуальной iOS, внутри Telegram:

1. холодный запуск, медленная сеть и повторный запуск из bfcache;
2. запуск при ошибке каждого опционального JS-файла;
3. Home → новый пост → назад → настройки → назад;
4. открытие/закрытие клавиатуры в AI и Composer;
5. выбор 10 фото, удаление среднего фото, восстановление draft;
6. Before/After: pan, pinch, rotate, resize, cancel, save;
7. входящие JPEG/PNG/WebP/HEIC и фото 12/24/48 МП;
8. AI cancel, offline, timeout, navigation-away и повторный запрос;
9. переход во внешний Telegram/VK и возврат;
10. memory warning/background/foreground во время редактирования.

Отдельно тот же базовый сценарий нужно сохранить на Android Telegram WebView,
чтобы iOS-исправления не создали платформенную развилку в business logic.
